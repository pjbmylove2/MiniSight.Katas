# P00 · 사과 공장 주말 특강 소개와 의도 · 멀티스레드·병렬처리·테스트 32시간

> 이 글은 주말 특강을 시작하면서 쓴 소개문이다. 무엇을 배우는지, 왜 이렇게 짰는지, 끝나면 무엇이 남는지를 먼저 적어 둔다.
> 기준: .NET Framework 4.7.2 / C# 7.3 / WinForms / x64. 새 NuGet 패키지는 쓰지 않는다.

## 1. 한 줄 소개

**"사과 공장"을 직접 만들면서 멀티스레드, 병렬처리, 테스트를 처음부터 배우는 주말 특강이다.** 주말 2번, 32시간(32교시)이다. 끝나면 포트폴리오로 보여 줄 수 있는 WinForms 프로그램 **PipelineLab**과 테스트가 남는다.

## 2. 누구를 위한 특강인가

- 회사 코드에서 `Thread`, `lock`, `Task`, `Invoke`를 **많이 읽었지만 직접 쳐 본 적은 거의 없는** 사람
- 장비 프로그램에서 "가끔 멈춘다", "가끔 숫자가 안 맞는다", "종료가 안 된다" 같은 문제를 만나 봤지만, **왜 그런지 말로 설명하기 어려운** 사람
- 바이브 코딩(AI가 짜 준 코드 붙여넣기)에 기대다가 **손으로 다시 짜는 힘**을 되찾고 싶은 사람

바로 나다. 지금까지 C# 초급 트랙(B01~B14)을 마쳤고, 주니어 트랙 Day09에서 `lock`, `Interlocked`, `volatile`, `CompareExchange`를 배우다가 이 특강으로 넘어왔다.

## 3. 무엇을 배우나: 사과 공장 이야기

특강 전체가 하나의 이야기로 이어진다.

```text
사진기(카메라)가 사과를 찍는다
  → 바구니(큐)에 담는다
  → 검사 일꾼들이 멍든 사과를 찾는다
  → 분류기(PLC 흉내)가 OK/NG 상자로 보낸다
  → 칠판(화면)에 숫자와 사진이 보인다
  → 채점 로봇(테스트)이 "제대로 했나"를 매번 확인한다
```

| 날 | 주제 | 배우는 것 | 그날 끝나면 화면에 보이는 것 |
|---|---|---|---|
| 1일차 (토) | 일꾼 | 스레드 만들기·기다리기, 백그라운드, 멈춤 신호, UI 스레드, 첫 테스트 | 사과 사진이 화면에 나온다 |
| 2일차 (일) | 같이 쓰기 | 경쟁 상태, `lock`, `Interlocked`, `CompareExchange`, `BlockingCollection`, 바구니 크기 제한 | 사과가 줄 서서 검사되고 OK/NG 숫자가 올라간다 |
| 3일차 (토) | 나눠서 빨리 | `Parallel.For`, 일꾼 수와 속도(암달의 법칙), `Task`, `async`/`await`, 취소 | 일꾼 1·2·4명 속도표가 나온다 |
| 4일차 (일) | 고장 찾기 | 데드락, 디버거 스레드 창, 감시견, 동시성 테스트, 안전한 정지 순서 | **작품 PipelineLab v1 + README** |

세 가지 주제가 섞여 있다.

- **멀티스레드**: 일꾼 여러 명이 동시에 일할 때 싸우지 않게 하는 법
- **병렬처리**: 일을 나눠서 더 빨리 끝내는 법, 그리고 나눠도 빨라지지 않는 이유
- **테스트**: "가끔" 생기는 문제를 **매번** 잡아내는 법

## 4. 왜 이렇게 짰나 (의도)

### 4-1. 왜 "초등학교 1학년" 눈높이인가

멀티스레드는 어려운 말이 너무 많다. 경쟁 상태, 원자성, 가시성, 메모리 배리어 같은 말부터 나오면 코드를 치기도 전에 지친다. 실제로 Day09에서 개념이 한 번에 여러 개 나오자 "눈에 안 들어온다"는 느낌이 왔다.

그래서 순서를 바꿨다. **비유 → 짧은 코드 → 돌려 보기 → 질문 1개.** 예를 들면 이렇다.

| 어려운 말 | 사과 공장 비유 |
|---|---|
| 코어 | 두뇌 (생각하는 자리) |
| 스레드 | 일꾼 |
| `Join` | "끝날 때까지 기다려" |
| `IsBackground` | 정규직과 알바 (알바는 문 닫으면 같이 퇴근) |
| UI 스레드 | 칠판은 담임선생님만 쓴다 |
| `lock` | 화장실 열쇠 (한 명씩만) |
| `Interlocked` | 번호표 기계 (안 겹치는 번호) |
| `CompareExchange` 깃발 | "사용 중" 팻말 (사용 중이면 지나간다) |
| `BlockingCollection` | 줄 서는 바구니 |
| 데드락 | 두 사람이 서로 상대 열쇠를 기다리며 영원히 서 있기 |

비유는 시작일 뿐이다. 매 교시 실제 C# 코드를 치고, 실제 출력을 보고, "무엇을 → 그래서 무슨 일이" 두 토막으로 설명할 수 있어야 넘어간다.

### 4-2. 왜 16시간이 아니라 32시간인가

처음 계획은 토·일 하루 8시간씩 16시간이었다. 그런데 1학년 눈높이로 하려면 개념 하나마다 비유, 타이핑, 실행, 질문이 **다** 들어가야 한다. 이걸 빼면 다시 "설명만 듣고 손은 못 쓰는" 상태로 돌아간다.

그래서 **개념 하나에 1교시(50분)** 를 쓰기로 했고, 자연스럽게 두 배인 32교시가 됐다. 대신 교시 하나는 조각 2~3개로 작게 쪼갠다.

### 4-3. 왜 작품을 WinForms로 만드나

공부만 하고 남는 게 없으면 금방 잊는다. 그래서 **교시마다 작품에 조금씩 붙인다.** 마지막 날 몰아서 만들지 않는다.

작품을 WinForms로 고른 이유는 세 가지다.

1. 내가 실제로 일하는 환경(FA 비전 검사 장비)이 WinForms다.
2. 멀티스레드 문제가 가장 잘 **보이는** 곳이 화면이다. 화면이 멈추고, 숫자가 튀고, 종료가 안 되는 게 눈에 보인다.
3. 면접이나 포트폴리오에서 "실행하면 바로 보이는 것"이 설명하기 좋다.

장비는 전부 **가짜(시뮬레이터)** 다. 가짜 카메라가 사과 그림을 만들고, 가짜 PLC가 OK/NG를 받는다. 실제 장비나 회사 코드는 쓰지 않는다.

### 4-4. 왜 테스트를 같이 배우나

현장에서 가장 무서운 버그는 "가끔" 생기는 버그다. 100번에 한 번 숫자가 틀리고, 하루에 한 번 화면이 멈춘다. 이런 건 눈으로 돌려 봐서는 잡기 어렵다.

그래서 1일차부터 **채점 로봇(MSTest)** 을 만든다. 처음에는 함수 하나를 확인하는 쉬운 테스트로 시작한다. 4일차에는 일부러 순서를 꼬아서 경쟁 상태를 **매번** 재현하는 테스트와, `Dispose`가 딱 한 번만 일어나는지 확인하는 테스트까지 간다.

## 5. 끝나면 무엇이 남나: PipelineLab v1

| 영역 | 내용 |
|---|---|
| 화면 | 사진기 최대 4대의 최신 사과(OK 초록 / NG 빨강 테두리), 찍은·OK·NG·버린·잃은 수, 바구니 높이, 일꾼 수별 속도표 |
| 동작 | 사진기 4대 × 초당 30장에서 화면이 멈추지 않는다. 10분 돌려도 잃은 수 0, 중복 0, 순서 뒤바뀜 0 |
| 고장 | 장애 버튼 4개(검사 느리게, 검사 중 예외, 팻말 안 되돌리기, 교착 모드)를 누르면 감시견이나 로그가 잡아낸다 |
| 정지 | 정지 버튼을 누르면 2초 안에 모든 일꾼이 퇴근하고, 돌려준 사진 수 = 만든 사진 수 |
| 테스트 | 초록색 테스트 8개 이상 (동시성 테스트 포함) |
| 문서 | README: 구조 그림, 실행 GIF, "어떤 문제를 어떻게 막았나" |

이 숫자들이 졸업 기준이다. "대충 돌아간다"가 아니라 **재서 확인할 수 있는** 기준으로 정했다.

## 6. 진행 방식

- 1교시 = 50분 + 쉬는 시간 10분. 교시 하나에 조각 2~3개.
- 조각마다 순서는 같다: 비유 한 줄 → 10~15줄 코드 → 처음 보는 단어 표 → 눈으로 보는 실험 1개 → 미리 확인한 예상 출력 → 질문 1개.
- 코드는 세 번 친다: 보면서 → 출력과 글자 단위로 비교 → 지우고 뼈대만 보고 다시.
- 한 줄짜리 `if`에도 `{ }`를 쓴다.
- 약 70% 이해하고 코드가 돌면 넘어간다. 남은 질문은 기록해 두고 다음에 다시 묻는다.
- 하루가 끝나면 그날 조각을 모아 글 하나로 정리한다 (1일차 → 4일차, 글 4편).

## 7. 이 특강이 끝나면 할 수 있어야 하는 것

1. 스레드를 만들고, 기다리고, 안전하게 멈추는 코드를 **손으로** 칠 수 있다.
2. `lock` / `Interlocked` / `volatile`을 언제 쓰는지 **이유와 함께** 말할 수 있다.
3. 화면이 멈추는 이유와 `BeginInvoke`로 고치는 법을 설명할 수 있다.
4. 일꾼을 늘려도 빨라지지 않는 이유를 숫자로 보여 줄 수 있다.
5. 데드락이 난 프로그램에서 디버거로 **어느 일꾼이 무엇을 기다리는지** 찾을 수 있다.
6. "가끔" 생기는 동시성 버그를 **매번** 재현하는 테스트를 쓸 수 있다.
7. 이 모든 걸 보여 주는 작품 하나를 GitHub에 올려 두고, 5분 안에 설명할 수 있다.
