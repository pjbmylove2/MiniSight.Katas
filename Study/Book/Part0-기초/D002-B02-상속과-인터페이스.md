# D002 · B02 상속과 인터페이스 (`class :` `base` `virtual` `override` `abstract` `interface` `sealed` `is`)

> 레벨 L0 · 지옥 레벨 ★2 · 약 2시간 · Kata 파일: 포트폴리오 `Katas/L0/D002.cs`
> 상태: **완료 (△ 통과, 2026-11-20)** — 기록은 맨 아래 "기록" 절

## 1. 오늘 할 수 있게 되는 것

1. `class 자식 : 부모`로 공통 코드를 물려받고, `: base(...)`로 부모 생성자를 먼저 부른다.
2. `virtual`/`override`로 "명령은 하나, 동작은 객체마다"를 만든다.
3. `abstract`로 "순서는 부모가, 빈칸은 자식이" 채우는 뼈대(템플릿 메서드)를 만든다.
4. `interface`로 "이것만 할 줄 알면 된다"는 약속을 세우고, 장비 없이 가짜 카메라를 끼운다.
5. `sealed`로 상속을 끊고, `is`로 실제 객체를 확인한다.
6. 예외도 상속을 따른다는 것(부모 catch가 자식 예외를 잡는다)과 catch 순서 규칙을 안다.

## 2. 🧒 비유

- **상속 = 사양서 물려받기.** "카메라 기본 사양서"(이름, 자기소개)를 에어리어 카메라 사양서가 그대로 따르고, 가로 픽셀만 덧붙인다.
- **virtual/override = 공장장의 "찍어!"** 공장장은 한 마디만 한다. 에어리어 카메라는 한 장, 라인 스캔 카메라는 한 줄씩 찍는다. 공장장은 누가 누군지 몰라도 된다.
- **abstract = 빈칸 있는 매뉴얼 서식.** "① 연다 → ② 결과 보고" 순서는 정해져 있고, "어떻게 여는지" 칸만 장치마다 채운다. 빈칸 있는 서식은 그대로는 못 쓴다.
- **interface = 자격증.** 가족(상속)이 아니어도 "이름 대기, 찍기" 자격만 있으면 시퀀스에 끼울 수 있다.
- **sealed = "이 문서로 새 사양서 만들지 말 것" 도장.** **is = 출입문 직원.** 겉옷(변수 형식)이 아니라 사람(실제 객체)을 보고 판단한다.

## 3. 본문

### 3-1. 상속과 생성 순서

`class AreaCam : CamBase`라고 쓰면 `AreaCam`은 `CamBase`의 멤버(`Name`, `Describe()`)를 한 줄도 다시 쓰지 않고 가진다.

`new AreaCam("CAM1", 1920)`을 하면 **부모 생성자가 먼저** 돌아 `Name`을 채우고, 그다음 자식 생성자 본문이 `Width`를 채운다. 부모 칸이 먼저 준비돼야 자식이 그 위에 쌓을 수 있기 때문이다.

`: base(name)`은 "부모 생성자에 `name`을 넘겨 먼저 실행하라"는 뜻이다. 이걸 안 쓰면 컴파일러가 몰래 `: base()`(인자 없는 부모 생성자 호출)를 넣는다. 그래서 **부모에 인자 없는 생성자가 없을 때** `: base(...)`를 꼭 써야 한다. `CamBase`처럼 생성자를 하나라도 직접 만들면 C#은 기본 생성자를 자동으로 만들어 주지 않는다. 빼면 CS7036이다.

### 3-2. `virtual` / `override` — 실제 객체가 고른다

- 부모의 `virtual`은 "자식이 바꿔도 된다"는 허락이고, 기본 동작(본문)이 있다.
- 자식의 `override`는 "그 메서드를 내 방식으로 다시 쓴다"는 선언이다.

`CamBase cam = new LineCam("CAM2"); cam.Grab();`에서 변수 형식은 `CamBase`지만, `virtual`+`override` 짝이 맞으면 C#은 **실제 객체(`LineCam`)**의 `Grab()`을 실행한다(동적 바인딩, 다형성). 그래서 검사 시퀀스는 `foreach (CamBase cam in cams) { cam.Grab(); }` 한 줄로 끝나고, 새 카메라 종류가 생겨도 이 루프는 고치지 않는다.

`override`를 빠뜨리면 **빌드는 성공**하고 경고 CS0114("…멤버를 숨깁니다")만 뜬다. 이때 C#은 **변수 형식** 기준으로 골라 부모의 `Grab()`이 불린다(정적 바인딩). 한 줄로: **override가 있으면 객체를 보고, 없으면 변수를 본다.**

### 3-3. `abstract` — 순서는 부모가, 빈칸은 자식이

- `abstract class`는 `new`할 수 없는 미완성 부모다(CS0144).
- `abstract` 메서드는 본문이 없고(`;`로 끝남, 본문을 쓰면 CS0500), 자식이 반드시 `override`해야 한다(안 하면 CS0534). abstract 메서드는 abstract 클래스 안에만 둘 수 있다(CS0513).
- `protected`는 자기 클래스와 자식 안에서만 보인다.

`DeviceBase`는 `public Start()` 안에 "열기 → 성공이면 '시작', 실패면 '열기 실패' 보고" 순서를 담고, 여는 법 `Open()`만 `protected abstract`로 비워 둔다. 바깥은 `Start()`만 부르면 된다. `Open()`을 바깥에 열어 두면 누가 `Open()`만 따로 불러 **보고(로그)가 건너뛰어진다.** 그래서 숨긴다. 이 모양을 **템플릿 메서드 패턴**이라고 한다(J04에서 상태 머신과 함께 다시 다룬다).

| 비교 | `virtual` | `abstract` |
|---|---|---|
| 본문 | 있다(기본 동작) | 없다 |
| 그 클래스를 `new` | 된다 | abstract 클래스라 안 된다 |
| 자식의 `override` | 선택 | 필수 |

### 3-4. `interface` — 자격만 맞춘다

`interface ICam { string Name { get; } string Grab(); }`은 본문 없이 멤버 목록만 있는 약속이다. C# 7.3에서는 인터페이스에 본문을 넣을 수 없고 멤버 앞에 `public`도 쓰지 않는다. `class X : ICam`이라고 했는데 멤버 하나라도 빠지면 CS0535다.

| 비교 | 클래스 상속(`abstract class` 포함) | `interface` |
|---|---|---|
| 몇 개를 붙이나 | 부모 하나 | 여러 개 (`: ICam, IDisposable`) |
| 코드(본문)를 물려받나 | 물려받는다 | 약속만 준다 |

`FakeCam`에 필요한 건 `Name`과 `Grab()`뿐이다. `CamBase`를 상속하면 `Describe()`, 기본 `Grab()` 같은 필요 없는 것까지 딸려 온다. 그래서 `FakeCam : ICam`으로 약속만 지킨다. 부모 `CamBase`가 `ICam`을 구현하면 자식 `AreaCam`도 자동으로 `ICam`이다. **검사 시퀀스가 `ICam`만 알게 하면** 사무실에서는 가짜, 현장에서는 진짜를 시퀀스 수정 없이 바꿔 끼운다.

### 3-5. `sealed`와 `is`

- `sealed class`는 자식을 만들 수 없다(CS0509). 동작이 바뀌면 안 되는 시뮬레이터·값 객체를 지킨다. `string`도 sealed다.
- `x is T`는 **실제 객체**를 `T`로 볼 수 있으면(`T` 자신, 자식·손자, 인터페이스 구현) true다. null이면 false. `CamBase cam = new SimAreaCam(...)`에서 `cam is AreaCam`이 True인 것은 실제 객체 `SimAreaCam`이 `AreaCam`을 상속하기 때문이다.
- 문자열 연결에서는 `"…" + (cam is AreaCam)`처럼 괄호가 꼭 필요하다. `+`가 먼저 계산되면 문자열에 `is`를 묻게 된다.

### 3-6. 예외도 상속이다

```text
Exception
 └ SystemException
    └ ArgumentException
       └ ArgumentNullException
```

catch는 **같은 형식 또는 그 자식 형식**을 잡는다. `catch (ArgumentException)`이 `ArgumentNullException`을 잡고, `ex.GetType().Name`은 실제 형식 "ArgumentNullException"을 알려 준다. catch는 위에서부터 맞춰 보므로 부모를 위에 두면 아래 자식 catch는 절대 실행될 수 없다. 그래서 컴파일러가 막는다(CS0160). **좁은 것(자식) → 넓은 것(부모)** 순서로 쓴다.

`CamBase b = a;`는 참조 형식 대입이라 새 객체가 생기지 않는다. `ReferenceEquals(a, b)`가 True다(D001·D002 조각 0의 값/참조 차이).

### 3-7. 흔한 실수

1. 자식에서 `override`를 빠뜨림 → 경고만 나고 기본 동작이 돈다(현장: "새 카메라가 기본 동작만 해요").
2. `: base(...)`를 빼먹음 → CS7036. 자식 생성자 안에서 `Name = name;`을 쓰려 해도 읽기 전용이라 안 된다.
3. 기본 동작이 있어야 하는 메서드를 `abstract`로 씀 → CS0500·CS0513, 클래스를 abstract로 바꾸면 이번엔 `new`가 CS0144.
4. 시퀀스 코드에서 변수를 `AreaCam` 같은 구체 클래스로 받음 → 가짜 카메라를 못 끼운다.
5. `catch (Exception)`를 맨 위에 둠 → 모든 예외를 삼켜 원인을 숨긴다.

### 조각 1 · 상속 — 부모가 가진 것을 물려받는다

```csharp
public static void Chunk1()
{
```

```csharp
public static void Chunk2()
```

### 조각 3 · `abstract` — 순서는 부모가, 빈칸은 자식이

```csharp
public static void Chunk3()
{
    DeviceBase ok = new LightDevice("LIGHT1", true);
    DeviceBase ng = new LightDevice("LIGHT2", false);
    Console.WriteLine(ok.Start());
    Console.WriteLine(ng.Start());
}

public abstract class DeviceBase
{
    public string Name { get; }

    protected DeviceBase(string name)
    {
        Name = name;
    }

    protected abstract bool Open();

    public string Start()
    {
        if (Open())
        {
            return Name + " 시작";
        }
        return Name + " 열기 실패";
    }
}

public class LightDevice : DeviceBase
{
    private bool Connected { get; }

    public LightDevice(string name, bool connected) : base(name)
    {
        Connected = connected;
    }

    protected override bool Open() => Connected;
}
```

| 키워드 | 역할 | 같은 뜻의 긴 말 |
|---|---|---|
| `abstract class` | `new`할 수 없는 미완성 부모 | "틀일 뿐, 자식을 통해서만 만든다" |
| `abstract` 메서드 | 본문 없음, 자식이 반드시 채움 | "virtual인데 기본 동작이 없고 override가 의무" |
| `protected` | 자기 클래스와 자식 안에서만 보임 | "바깥(Main 등)에서는 부를 수 없음" |
| `private` | 그 클래스 안에서만 보임 | "자식도 바깥도 못 봄" |

출력:
```text
LIGHT1 시작
LIGHT2 열기 실패
```

- **실험:** `DeviceBase ng = new DeviceBase("LIGHT2");`로 바꾸고 빌드 → `error CS0144: 추상 형식 또는 인터페이스 'DeviceBase'의 인스턴스를 만들 수 없습니다.` (덤: `LightDevice`의 `Open()`을 지우면 CS0534)
- **질문:** `DeviceBase`를 `abstract`로 만든 이유는? `Open()`에 본문이 없다는 점과 `new DeviceBase(...)`를 허락했을 때 `Start()`에서 생길 일을 연결하라.

### 조각 4 · `interface` — "이것만 할 줄 알면 된다"는 약속

```csharp
public static void Chunk4()
{
    ICam[] cams = { new FakeCam("SIM1"), new AreaCam("CAM1", 1920) };
    foreach (ICam cam in cams)
    {
        Console.WriteLine(cam.Grab());
    }
    Console.WriteLine(cams[0].Grab());
}

public interface ICam
{
    string Name { get; }
    string Grab();
}

// CamBase 선언을 고친다
public class CamBase : ICam

public class FakeCam : ICam
{
    private int _count;

    public FakeCam(string name)
    {
        Name = name;
    }

    public string Name { get; }

    public string Grab()
    {
        _count++;
        return Name + ": 가짜 사진 #" + _count;
    }
}
```

| 키워드 | 역할 | 같은 뜻의 긴 말 |
|---|---|---|
| `interface` | 멤버 목록만 있는 약속 | "본문 없는 public abstract 멤버만 모은 형식" |
| `class X : ICam` | 약속을 지키겠다는 선언 | "ICam의 모든 멤버를 public으로 구현한다" |
| `I`로 시작하는 이름 | 인터페이스 이름 관례 | (규칙은 아니고 관례) |
| `_count++` | 필드 값을 1 늘림 | `_count = _count + 1;` |

출력:
```text
SIM1: 가짜 사진 #1
CAM1: 한 장 촬영 1920px
SIM1: 가짜 사진 #2
```

- **실험:** `FakeCam`에서 `Grab()`을 지우고 빌드 → `error CS0535: 'FakeCam'은(는) 'ICam.Grab()' 인터페이스 멤버를 구현하지 않습니다.`
- **질문:** `FakeCam`은 `CamBase`의 자식이 아닌데 어떻게 `AreaCam`과 같은 `ICam[]`에 들어가나?
- 3줄째가 `#2`인 이유: `cams[0]`은 루프에서 쓴 **같은 FakeCam 객체**라 `_count`가 이미 1이었다.

| 키워드 | 역할 | 같은 뜻의 긴 말 |
|---|---|---|
| `sealed` | 이 클래스로 자식을 못 만들게 막음 | "이 클래스가 상속의 마지막" |

출력:

## 6. 현장 연결

- **장비 SW:** 장치는 `ICam`(자격) → `CamBase`(공통 코드) → `AreaCam`·`LineCam`(장치별) 3층으로 많이 짠다. 검사 시퀀스는 `ICam`만 알게 해서 사무실에서는 `FakeCam`, 현장에서는 실제 카메라를 끼운다. 장치 시작 순서는 abstract 부모의 `public Start()` 한 곳에 두고, 장치마다 다른 부분만 `protected abstract`로 비운다. 누가 부품 메서드만 따로 불러 순서·로그를 건너뛰는 사고를 구조로 막는다.
- **TS:** "새 카메라를 붙였는데 기본 동작만 한다" → 새 클래스 메서드의 `override` 누락을 의심하고, 빌드 로그에서 **CS0114 '…멤버를 숨깁니다'** 경고를 증거로 찾는다(증상 → 가설 → 증거). 핵심 경고는 프로젝트 설정에서 "경고를 오류로"에 올려 두면 빌드에서 막힌다. 빌드 에러가 여러 개면 맨 위(첫 에러)부터 본다. 뒤 에러는 연쇄인 경우가 많다(CS0509 → CS1729).
- **산업별:** 반도체·디스플레이·2차전지 모두 장치 종류가 바뀌어도 시퀀스가 그대로여야 한다. 현장마다 카메라·조명·PLC 벤더가 달라도 인터페이스 뒤에 숨기면 시퀀스 수정 없이 대응한다. J03(인터페이스·계약), J05(Factory·Adapter)로 이어진다.

<details>
<summary>정답</summary>

1. 부모 `CamBase` 생성자가 먼저, 그다음 `AreaCam` 본문. 부모에 인자 없는 생성자가 없을 때 꼭 쓴다(안 쓰면 컴파일러가 넣는 `: base()`가 실패, CS7036).
2. `virtual`은 본문이 있고, 그 클래스를 `new`할 수 있고, `override`는 선택. `abstract`는 본문이 없고, abstract 클래스라 `new` 불가, `override` 필수.
3. 빌드 성공 + 경고 CS0114. `CAM2: 기본 촬영`. override가 없으면 변수 형식(`CamBase`) 기준으로 메서드를 고른다.
4. 클래스 상속은 하나, 인터페이스는 여러 개. 본문은 클래스 상속만 물려준다. `FakeCam`에 필요한 건 `Name`과 `Grab()`뿐이라, `CamBase`를 상속하면 필요 없는 것까지 딸려 온다.
5. catch는 위에서부터 맞추고 같은 형식 또는 자식 형식을 잡는다. 부모가 먼저 다 잡으니 자식 catch는 실행될 수 없어 CS0160. 자식을 위, 부모를 아래로.

### 곁가지 질문

> **Q. 대기열 12번: `Stop()`을 두 번 부르면 죽나? (D001 오해 재발)**
> 답: 안 죽는다. 죽는 건 Start 전에 Stop을 부를 때다(`_timer`가 아직 null). Dispose는 객체를 정리할 뿐 변수는 그대로라, 멈춘 뒤에도 `_timer != null`이 참이다. 그래서 `_timer = null;`을 짝으로 쓴다.
> 확인 실험: `System.Threading.Timer`로 Start 전 Stop → NullReferenceException. Start → Stop 뒤 `IsRunning => _timer != null`이 `True`. `if (_timer == null) { return; } _timer.Dispose(); _timer = null;`로 고치면 `False`.

> **Q. 조각 5 실험에서 CS0509 말고 CS1729는 왜 같이 떴나?**
> 답: sealed 상속이 거부되자 컴파일러가 `TestCam`의 부모를 `object`로 보고 계속 검사했다. `: base(name)`이 `object` 생성자에 인자 1개를 넘기는 꼴이 되어 CS1729가 연쇄로 났다. 진짜 원인은 첫 에러다.
> 확인 실험: csc 7.3 명령줄은 CS0509만, VS 오류 목록은 CS0509 + CS1729를 보였다.

> **Q. ③을 `abstract`로 쓰면 왜 안 되나?**
> 답: abstract 메서드는 본문을 가질 수 없고(CS0500), abstract 클래스 안에만 둘 수 있다(CS0513). 클래스를 abstract로 바꾸면 Chunk2의 `new CamBase("CAM3")`가 CS0144로 막힌다. 기본 동작이 있고 직접 만들 수도 있어야 하니 `virtual`이다.
> 확인 실험: 사용자 저장본(③ = `abstract`)을 직접 빌드해 CS0500·CS0513 확인.
